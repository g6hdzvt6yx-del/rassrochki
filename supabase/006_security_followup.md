# Миграция 006_security_followup — что она меняет

Продолжение аудита безопасности от 03.11.2026 для облака «rassrochki» (Eppaz).

**Обновлено 10.11.2026.** Скрипт приведён к текущей базе: применяется после `009_expense_period.sql`,
восстановление копии и корзины учитывает реестр расходов. Заодно исправлена ошибка из `008_expenses.sql`:
восстановление копии, в которой есть расходы, останавливалось с ошибкой «malformed array literal»
(строка `tables := tables || 'expenses'`). Копии, сделанные до появления расходов, восстанавливались нормально.
Файлы рядом:

| Файл | Зачем |
|---|---|
| `006_precheck.sql` | Проверка перед миграцией. Только читает, ничего не меняет. Показывает номера договоров и платежей с недопустимым чеком (без содержимого). |
| `006_security_followup.sql` | Сама миграция. Одна транзакция: при любой ошибке не меняется ничего. |
| `006_security_followup_rollback.sql` | Откат к состоянию после 009 (до 006), если понадобится. |

Данные договоров, платежей и клиентов миграция **не меняет**. Добавляется только служебное поле версии и таблица приглашений.

## Порядок применения

1. Supabase → SQL Editor → вставить `006_precheck.sql` → Run. Пустой результат — можно продолжать.
   Если есть строки — это договоры с подозрительным чеком; их надо разобрать до миграции (миграция сама остановится и ничего не изменит).
2. SQL Editor → `006_security_followup.sql` → Run. В конце файла — запросы для проверки.
3. Слить pull request (сайт). Порядок 2 и 3 можно поменять: новый сайт работает и со старой базой, старый сайт — с новой.

## 1. Серверная проверка чеков (находка 1)

Как устроены платежи: `contracts.payments` — объект `{"0": {...}, "1": {...}, "__contacts": [...]}`.
У платежа чеки лежат в `receipts` (массив) и/или в старом поле `receipt`. Чек — файл в бакете
(`{name, type, path}`) или встроенная копия с Mac (`{name, dataUrl}`).

Новое ограничение `contracts_receipts_safe` не пропускает:
- `dataUrl`, который не фото (JPEG/PNG/WebP/HEIC) и не PDF в base64 — то есть `javascript:…`, HTML, SVG и т. п.;
- `path`, который начинается с `/`, содержит `..`, `\`, `:` или `//` (ссылку вместо пути, выход из папки);
- `receipts`, который не массив; `payments`, который не объект.

Это страховка за сайтом: даже если кто-то с доступом руководителя пишет прямым запросом
или подсовывает чек через корзину, подделка в базу не попадёт. Проверено на копии схемы:
8 видов подделки отклонены, настоящие чеки и контакты проходят.

Суммы и даты платежей сервер по-прежнему не проверяет (см. «Что осталось»).

## 2. Версия строки updated_at (находка 8)

- У `contracts`, `investors`, `withdrawals` появляется `updated_at`. Расходы (`expenses`) сайт пишет напрямую, им версия не нужна.
- Его ставит триггер `touch_row` при каждом изменении. Значение, присланное с сайта, игнорируется.
  Изменение, которое ничего не меняет, версию не сдвигает.
- Сайт пишет с условием `id = … and updated_at = <версия, которую видел пользователь>`.
  Если за это время договор изменили на другом устройстве, запись не проходит, и сайт
  сначала пробует аккуратно объединить изменения (разные платежи — оба сохраняются),
  а если правили одно и то же — показывает:
  «Эту запись уже изменили на другом устройстве или в другой вкладке. Ваше изменение не сохранено,
  чтобы не затереть чужие данные. Нажмите «↻» (обновить), проверьте запись и повторите действие.»
- Раньше сайт сравнивал все поля строки, включая весь JSON платежей, прямо в адресе запроса.
  С встроенным чеком на 200 КБ адрес получался 200 000 символов и запрос не проходил.
  Теперь адрес — около 110 символов.
- Восстановление копии версию из копии не переносит: версию всегда ставит база.

## 3. Журнал (остаточные риски находки 2)

**3а. Сбой записи в журнал.** Раньше триггер `audit_row_change` при ошибке записи в `action_log`
писал предупреждение и пропускал изменение — договор менялся без следа. Теперь ошибка
отменяет всю операцию, а сайт показывает «Изменение не сохранено: не удалось записать его в журнал…».
Почему так, а не «сохранить, а запись в журнал потом»: в финансовой программе изменение без
следа хуже, чем повтор действия. Если журнал откажет надолго, сайт перестанет сохранять — это
заметно сразу, а не через месяц при сверке.

**3б. Восстановление построчно.** `restore_backup` и `restore_trash_item` раньше выключали
журнал (`rassrochki.skip_audit`) и оставляли одну сводную запись. Теперь журнал работает,
а каждая запись помечена источником:
- восстановление копии: «Изменение»/«Изменение платежа» по каждому изменённому договору,
  вкладчику, выводу; «Перемещение в корзину» по каждому убранному; источник —
  «Восстановление копии от ДД.ММ.ГГГГ ЧЧ:ММ». Сводная запись «Восстановление копии» осталась;
- восстановление из корзины: «Восстановление» с полными данными строки или «Восстановление
  чека»; источник — «Корзина».
В «Истории» сайта источник показан рядом с именем сотрудника.

`skip_audit` оставлен только для ручного обслуживания базы в SQL Editor: сайт включить его не может.

## 4. Операторы по приглашению (находка 10)

Было: руководитель вводил почту, и `set_operator` сразу делал эту учётную запись оператором.
По тексту ошибки было видно, зарегистрирована ли почта, а любую «свободную» учётную запись
в общей базе можно было забрать себе.

Стало:
1. Руководитель: «Операторы и назначения» → «Пригласить оператора» → почта и имя →
   «Создать приглашение». Сайт показывает одноразовую ссылку — её надо отправить оператору.
   Ответ одинаковый, есть такая учётная запись или нет.
2. Учётную запись оператору создают в Supabase → Authentication → **Invite user**:
   письмо приходит оператору, пароль он задаёт сам.
3. Оператор открывает ссылку, входит под своей почтой и нажимает «Принять приглашение».
   Только после этого он становится оператором.

Правила: почта должна совпасть и быть подтверждённой; ссылка действует 7 дней и срабатывает
один раз; новое приглашение на ту же почту отменяет старое; не больше 20 приглашений в сутки;
в базе хранится только отпечаток кода (sha256); учётную запись из чужого кабинета так не забрать.
`set_operator` теперь только блокирует/разблокирует и переименовывает уже принятых операторов.
Всё пишется в журнал: «Приглашение оператора», «Оператор принял приглашение», «Приглашение отозвано».

## Что проверено

Локально, PostgreSQL 16 + PostgREST 12, копия схемы облака (собрана из каталога: функции,
политики, права, триггеры), вымышленные данные:
- `test_006.py`: 29 из 29 проверок после миграции (в том числе восстановление расходов из копии и из корзины); до миграции те же проверки показывают
  все три проблемы (подложный чек принят, изменение без журнала сохранено, чужая учётная запись стала оператором);
- откат: схема после `006` + `rollback` совпадает со схемой до `006` (pg_dump без отличий);
- миграция на базе с подложным чеком останавливается и ничего не меняет;
- два «устройства» через настоящий клиент сайта: устаревшая запись отклонена с понятным
  сообщением, разные платежи объединены, журнал корректный;
- собранный сайт в Chrome под CSP: все разделы, PDF, печать, Excel, приглашение оператора от
  создания до входа оператора — без нарушений CSP и ошибок.

## Что осталось (не в этой миграции)

- Суммы и даты платежей проверяет только браузер. Прямым запросом руководитель (или украденная
  сессия) может записать оплату 99 999 999 ₽, задним числом или отрицательную цену договора —
  проверено, сервер принимает. Теперь это хотя бы всегда попадает в журнал. Исправление — приём
  платежа через серверную функцию с проверкой суммы и даты (как add_payment в аудите ФинУчета).
- Защита от утёкших паролей в Supabase доступна только на тарифе Pro.
