Что проверено: код живого сайта (ветка `codex/web-version`, именно она публикуется),
база данных Supabase `rassrochki` (права доступа, серверные функции, хранилище чеков,
резервные копии), зависимости, история Git на утечку ключей.

## Итог простыми словами

**Сам код и база сделаны хорошо.** Взломать сайт «через код» по найденному — нельзя:

- Все 10 таблиц закрыты (RLS включён). Без входа данные не видны никому.
- Оператор видит только назначенных ему клиентов и только телефон/график —
  без наценок, вкладчиков, чеков и паспортов.
- Все 14 серверных функций проверяют права перед действием. Предупреждение
  Supabase о них — ложная тревога, проверено вручную.
- Чеки доступны только администратору (по временной ссылке на 60 секунд).
- Секретных ключей в публичном репозитории нет, только публичный ключ — так и должно быть.
- Уязвимостей в библиотеках: 0. Мест для XSS-атак (внедрения кода) не найдено.
- Ежедневная автокопия базы работает, копии хранятся 90 дней.

**Главные риски — не в коде, а в аккаунтах и настройках.** Сайт «угонят» не через
программу, а через вашу почту, GitHub или пароль.

## Что исправить — по важности

### 🔴 Критично (сделать сегодня, всё в настройках, без кода)

1. **Двухфакторная защита (2FA) на почте `nohchoi@bk.ru`.**
   Через «Забыли пароль?» владелец почты получает сайт целиком.
   Mail.ru → Настройки → Безопасность → Двухфакторная аутентификация.

2. **2FA на GitHub.** Кто зайдёт в ваш GitHub — сможет выложить на сайт
   поддельную страницу входа и собрать пароли. github.com → Settings →
   Password and authentication → Enable two-factor.

3. **2FA на аккаунте Supabase** (supabase.com → Account → Security).
   Это «ключи от сейфа»: оттуда видна и удаляется вся база.

4. **Запретить регистрацию новых пользователей** (проверить не удалось — нужно
   посмотреть вручную). Supabase → Authentication → Sign In / Providers →
   Email → выключить **Allow new users to sign up**. Операторов вы и так создаёте
   вручную. Даже если сейчас включено — посторонний данных не увидит, но лишний
   аккаунт в системе не нужен.

### 🟠 Важно (на этой неделе)

5. **Внешняя резервная копия.** Автокопии лежат *в той же* базе. Если аккаунт
   Supabase взломают, проект удалят или заблокируют — пропадут и данные, и копии.
   Файлы чеков в копии не входят вовсе.
   *Варианты:* (а) раз в неделю нажимать выгрузку в Excel и сохранять файл на
   компьютер + облако; (б) тариф Supabase Pro ($25/мес) — ежедневные копии
   на стороне Supabase, без автоматической паузы проекта.

6. **Защитить ветку публикации.** Сайт собирается из `codex/web-version`, и
   любой push туда (в т.ч. от ИИ-ассистентов) сразу уходит на живой сайт.
   GitHub → Settings → Branches → Add rule для `codex/web-version`:
   «Require a pull request before merging». Тогда изменения попадут на сайт
   только после вашего нажатия «Merge».

7. **Включить защиту от утёкших паролей.** Supabase → Authentication →
   Passwords: включить *Leaked password protection*, минимальная длина 12.
   Пароли у вас и оператора — длинные и не используемые больше нигде.

8. **Применить скрипт `supabase/005_security_hardening.sql`** (готов в этой ветке):
   убирает старые слишком широкие правила для чеков, ставит лимит файлов
   (10 МБ, только фото/PDF), делает журнал действий неподделываемым.
   Работу сайта не меняет. Могу применить сам — скажите.

### 🟡 Желательно

9. **Персональные данные и закон.** В базе хранятся ФИО, телефоны и паспорта
   клиентов, а сервер Supabase стоит в Ирландии (`eu-west-1`). По 152-ФЗ
   (ст. 18, ч. 5) первичные данные граждан РФ должны храниться на серверах
   в России. Это юридический, а не технический риск — стоит уточнить у юриста.
   Если потребуется — переезд на российский хостинг (Yandex Cloud, Selectel).

10. **Публичный репозиторий.** Код виден всем. Это само по себе не дыра
    (защита держится на базе, а не на секретности кода), но злоумышленнику
    проще изучать. Сделать приватным можно, если перенести публикацию
    с GitHub Pages (на бесплатном тарифе требует публичный репозиторий)
    на Cloudflare Pages / Netlify / Vercel — все бесплатны и работают с приватными.

11. **Уборка веток.** В репозитории 6+ веток от ИИ-ассистентов и `main`,
    который сильно отстал от живой версии. Путаница = риск случайно выкатить
    старую версию. Стоит слить живую версию в `main` и публиковать из `main`.

12. **Отключить устаревший anon-ключ** (JWT) после перехода сборки на новый
    `sb_publishable_...` — Supabase → Settings → API Keys.

## Про «сайт ляжет»

- Объём: база 13 МБ из 500 МБ бесплатных, чеки 2,3 МБ из 1 ГБ. Запас — годы.
- Сайт — статичные файлы на GitHub Pages: падают очень редко.
- Слабое место — бесплатный Supabase: проект **ставится на паузу после 7 дней
  без активности** (ваш второй проект `rec` как раз на паузе). При ежедневной
  работе не грозит, но после отпуска сайт может «не открыться» — тогда зайти
  в supabase.com и нажать Restore. Тариф Pro это убирает.
- Архитектура кода (проверки прав в базе, корзина, журнал, автокопии,
  защита от одновременного редактирования) — для такого приложения выше среднего.
